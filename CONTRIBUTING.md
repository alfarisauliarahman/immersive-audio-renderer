# Contributing

Thank you for helping improve Immersive Audio Renderer. Contributions must preserve the project's central rule: describe only capabilities supported by verified source data.

Participation in project spaces is governed by [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md). General usage questions and bug-report requirements are documented in [SUPPORT.md](SUPPORT.md).

## Before starting

- Read [Architecture](docs/ARCHITECTURE.md) and [Format support and boundaries](docs/FORMAT_SUPPORT.md).
- Check the [Roadmap](docs/ROADMAP.md) and existing issues before starting a large change.
- Open a design discussion before changing the normalized scene contract, source capability semantics, cache format, or external renderer behavior.
- Report security problems privately according to [SECURITY.md](SECURITY.md).

## Development workflow

1. Create a focused branch.
2. Install locked dependencies with `npm ci`.
3. Make the smallest coherent change.
4. Add or update tests.
5. Update documentation and capability labels in the same change.
6. Run the checks in [Testing](docs/TESTING.md).
7. Review the staged diff for private media, generated output, absolute personal paths, and secrets.

Recommended checks:

```powershell
npm test
npm run build
cargo test --manifest-path src-tauri/Cargo.toml
git diff --check
```

## Source and capability rules

- Do not enable object solo, mute, or re-render unless independently addressable object PCM is bound to trustworthy metadata.
- Do not label diagnostic positions or reconstruction rows as authored objects.
- Do not call a finished stereo or binaural WAV an Atmos master.
- Preserve explicit labels for OpenJOC output, FFmpeg codec-core fallback, independent DAMF preview rendering, and visualization-only timelines.
- Fail closed when a source violates a format assumption.
- Keep external command invocation shell-free and path-safe.

## Media and provenance

Do not commit:

- commercial or website-ripped music;
- Dolby Visualizer WAV, MP3, or JSON assets without written redistribution permission;
- DAMF masters without an explicit redistributable license;
- chat exports, screenshots containing private information, caches, or user media;
- unverified installers, archives, codecs, or opaque executables.

Public fixtures must be generated by the project or have a clear license that permits repository and binary-release redistribution. Document the source, author, license, modifications, and expected hash.

## Dependencies

New runtime dependencies require:

- a concrete need not met by the existing stack;
- an active, reviewable upstream source repository;
- a license compatible with the project and intended distribution;
- an update to `THIRD_PARTY_NOTICES.md`;
- lockfile changes and test evidence;
- special review for bundled native binaries.

Never substitute an opaque downloadable installer for a source dependency.

## Pull request checklist

- [ ] Unit tests pass.
- [ ] Frontend production build passes.
- [ ] Relevant native and manual checks pass.
- [ ] Capability labels remain accurate.
- [ ] Documentation and changelog are updated.
- [ ] No third-party/private fixture entered the diff or Git history.
- [ ] New dependency licenses and notices are documented.
- [ ] No generated cache, build output, or local absolute path is committed.
